# Grasshopper 空间逻辑精讲

> 面向「已经有 Rhino 建模经验、想用 GH 做参数化 / 想把设计意图落成构造序列」的人。
> 不教按钮位置，教**为什么这样连**、**为什么结果不对**、**什么时候不该用 GH**。
> 配套：`grasshopper-component-index.md`（查组件）、`rhino-command-reference.md`（查命令语义）、`feature-recognition.md`（B-rep 与特征）。

---

## 1. 一句话定位

**Grasshopper 是把建模操作写成「数据流图」，它保存的是构造过程，不是结果几何。**

这句话不是修辞，是可以实测的：

```
2026-11-23 实测（E-019）
  画布上 14 个对象、18 条连线、Center Box 输出 10 个盒子、视口里清晰可见
  → Rhino 文档 doc.Objects.Count = 0
```

视口里看得到 10 个盒子，文档里一个实体都没有。因为 GH 只画**预览**（preview），要落地必须显式 **Bake**。
反过来，在 Rhino 里手动 `Box` 建 10 个盒子 → 文档里有 10 个 Brep，但**它们是怎么来的永远丢了**。

这就是你几天来一直在问的那件事的答案：

| | Rhino 手动建模 | Grasshopper | SolidWorks |
|---|---|---|---|
| 存的东西 | 结果几何（B-rep：面/边/trim 环） | **构造过程**（参数 + 组件 + 连线） | 操作意图（特征树节点） |
| 改尺寸 | 重画 / 缩放（几何变形） | **拖滑块，全图重算** | 改草图尺寸 |
| 改结构 | 手工重做 | 改连线 / 换组件 | 编辑特征 |
| 能"删掉一个倒角"吗 | ❌ 只能 Untrim + 重缝 | ✅ 前提是**当初就是用电池倒的** | ✅ 删特征节点 |
| 交互对象 | 视图里的几何 | 画布上的数据流 | 特征树 |

**关键结论（也是边界）：GH 给你"历史感"，但那份历史是「你亲手写下的」，不是「从结果反推出来的」。**

这正好和 `feature-recognition.md` 第 8、9 节闭环：

- 你自己建的模型 → 用 GH 建 → 天生可回退（不需要 FeatureWorks）
- 别人建的 / 导入的哑实体 → 只有 B-rep → FeatureWorks 走**逆向识别 + 人裁决**，天花板受不适定性限制
- 混接/拟合出来的面 → 连逆向都没得救（第 8 节三类操作表）

所以别指望 GH 能替代 FeatureWorks，也别指望 FeatureWorks 能达到 GH 的可编辑性——**它们解决的是两个方向的问题**。

### 三层对照（做插件时必须分清）

| 层 | 载体 | 你能做什么 | 不能做什么 |
|---|---|---|---|
| 命令层 | `Rhino.Commands`，1256 条（见 `rhino-command-index.md`） | 敲、录宏、脚本调用 | 拿不到中间数据 |
| 构造层 | GH 组件 2336 个（见 `grasshopper-component-index.md`） | 拿中间数据、任意重排顺序、参数扫掠 | 需要用户会 GH；不落地 |
| 内核层 | RhinoCommon（`Brep` / `Surface` / `Trim`） | 精确控制几何、做插件给非 GH 用户 | 没有现成"特征"概念，全部自己实现 |

**判断口诀**：要「给会用 GH 的人做探索」→ 构造层；要「给不会 GH 的人一键完成」→ 内核层 + 面板；要「快速验证一个想法」→ 先用命令层录一遍。

## 2. 三个基本单元，以及为什么组件必须"无副作用"

GH 画布上只有三种东西：

```
[参数 Param]  ──连线──▶  [组件 Component]  ──连线──▶  [参数 Param]
  数据容器                  纯函数                    数据容器
（滑块/点/曲线/曲面）    （输入→输出，不改输入）        （可继续被读取）
```

1. **参数（Param）**：数据的容器。滑块、数值、点、曲线、曲面、布尔都是参数。它还能挂**修饰符**（见 §3.3）。
2. **组件（Component）**：一个函数。给它输入，它输出新数据，**绝不修改输入**。
3. **连线（Wire）**：数据依赖关系。它同时决定**求值顺序**——GH 自动拓扑排序，不需要你排执行顺序。

"无副作用"是 GH 能重算的前提：任何一个参数变了，GH 只要把下游重跑一遍，结果必然一致。
如果组件会改输入（有副作用），重算就会依赖"上次跑到哪"，参数化立刻崩溃。

> **这条对写自定义组件（C# / Python）同样成立**：`SolveInstance` 里不要改输入数据、不要读全局状态、不要依赖调用顺序。
> 违反它的症状是"拖滑块时好时坏、重开文件结果不一样"。

## 3. 数据：Item / List / Tree —— GH 里九成"结果不对"的真正原因

### 3.1 三个层次

| 层次 | 长什么样 | 例子 |
|---|---|---|
| Item | 单个值 | 一个点 `{45,0,2}` |
| List | 一条有序序列，**一个分支** | 10 个点，路径 `{0}` |
| Tree | 多分支，每分支一条列表 | 8 条曲线 × 每条 6 点 = 8 个分支，路径 `{0}`…`{7}` |

**分支路径（path）就是地址**：`{2;1}` 表示"第 2 条曲线的第 1 段"。GH 用它记住"这个数据属于谁"，这是参数化能保持分组关系的关键。

### 3.2 匹配规则（最容易踩）

组件的输入分两种访问方式（`describe_component` 的 `access` 字段会告诉你）：

- **item access**：我只要一个值。如果喂给它一个 list，GH 会**自动逐个迭代**（隐式循环）。
- **list access**：我要整条列表一次（如 `Mass Addition`、`Sort List`、`Join`）。

当两个输入都是 list 时，按下面规则配对：

| 情况 | 行为 |
|---|---|
| 一边单值、一边列表 | **单值广播**到全表（最常用） |
| 两边等长 | **一一对应**（index 对齐） |
| 两边不等长 | 默认按**最短**截断（部分组件可选 longest + 循环重复） |
| 分支路径不同 | 按 **path 匹配**，不同 path 不互相干扰 |

**本次演示就是靠这条规则工作的**：`Multiplication` 的 `A` 收到 10 个数的列表、`B` 收到 1 个滑块 → 广播；`Center Box` 的 `Base`（10 个平面）、`X/Y/Z`（10 个尺寸）→ 一一对应，一次出 10 个盒子。

**排查口诀**：结果数量不对 → 先数每个输入的 item 数；数量对但配错对 → 查 path 是否一致；一个变多个/多个变一个 → 十有八九是 Graft/Flatten 位置错了。

### 3.3 四种结构修饰符（官方 13 种里最常用的 4 个）

| 修饰符 | 作用 | 典型场景 | 风险 |
|---|---|---|---|
| **Flatten** | 所有分支压成一条 list | "我不在乎分组，全给我处理" | 丢失归属关系，之后再想分组就难了 |
| **Graft** | 每个 item 单独成一个分支 | 让 `n×1` 和 `1×m` 变成 `n×m` 两两组合 | 分支数爆炸，几十个点就上千分支 |
| **Simplify** | 去掉所有分支共有的路径索引 | 清掉组件自动追加的无用索引（一串 0） | 过度简化可能让本该分开的合并 |
| **Renumber** | 按出现顺序重编号 | 只要顺序、不要原结构 | 抹掉所有相关性信息 |

官方对 Graft/Flatten 的定位很直接：*"often needed when a component pairs up input values in unwanted ways"* —— 它们不是"高级技巧"，是**修正匹配**的工具。
所以判断标准不是"要不要用"，而是"**我想要什么样的配对**"。

修饰符可以挂在参数上（右键 → Flatten/Graft/Simplify），也可以插 `Flatten`/`Graft` 组件。
区别：**挂输入 = 组件运算前转换；挂输出 = 运算后转换**（`grasshopperprimer` 原文）。位置选错，结果就错。

## 4. 构造序列设计法：把"天马行空"翻译成电池

McNeel 官方指南给了一个通用四步（*Essential Algorithms and Data Structures* 1.3）。我把它改写成**建模语境**，并补上第 5 步（验证）——因为官方指南里没有强调"怎么证明你做对了"：

### 第 1 步 · 写清意图（一句话，可被否证）

> ❌ "做一个渐变的东西"（无法验证）
> ✅ "10 个立方体，第 i 个半径 = i × 基准 × 2，底面都在 z=0，沿 X 等距排开"（可数、可量、可截图对比）

**这一步省不得**。意图含糊，后面所有调试都变成猜。

### 第 2 步 · 列出自由度（哪些是参数，哪些是常量）

本次演示的自由度清单：

| 参数 | 含义 | 范围 | 默认 |
|---|---|---|---|
| `N` | 个数 | 1–30 | 10 |
| `起始序号` | 序列起点（决定最小尺寸） | 0–10 | 1 |
| `基准半径` | 第 1 个的半径基准 | 0.1–5 | 1.0 |
| `半径倍率` | 每个半径乘多少 | 0.5–6 | 2.0 |
| `间距` | 相邻中心距 | 10–150 | 45 |
| `Y偏移` | 整排的位置 | 0–300 | 0 |

**判据**：凡是"我可能会想改一下试试"的量，就做成滑块；凡是"这是物理常数/规范"的量，写成常量。
滑块太多会淹没重点，太少就不是参数化。

### 第 3 步 · 拆成几何步骤（每步只做一件事）

```
① 生成序号        1 … N                     Series
② 序号 → 半径      序号 × 基准 × 倍率        Multiplication ×2
③ 半径 → 边长      半径 × 2                  Multiplication
④ 序号 → 位置      序号 × 间距               Multiplication
⑤ 数值 → 坐标轴    点(X, Y, 半径) + XY 平面   Construct Point + XY Plane
⑥ 坐标轴 + 尺寸 → 几何                       Center Box
```

注意 **Z 中心 = 半径** 这个设计：因为边长 = 2×半径，把中心抬到"半径"高度，底面正好落在 z=0。
**一条数值关系就省掉了一步 `size/2` 的除法**。这类"用几何关系消掉一个组件"是构造序列设计里最划算的技巧。

### 第 4 步 · 定数据结构（每个输出是 Item 还是 List？长度多少？）

| 输出 | 类型 | 长度 | 备注 |
|---|---|---|---|
| 序号 | List | N | 一个分支 |
| 半径 | List | N | 广播 `基准`、`倍率` |
| 边长 | List | N | |
| 位置 X | List | N | |
| 点 / 平面 | List | N | 三个坐标都是 List(N) |
| 盒子 | List | N | 四个输入都是 List(N)，一一对应 |

**这一步写完，画布该怎么连基本就确定了**。绝大多数"连不对"，是因为根本没想过这一步。

### 第 5 步 · 验证（官方指南没强调，但这是分水岭）

GH 的求解器**只保证"算完了"，不保证"算对了"**。必须三件套：

1. **数量验证**：每个关键输出的 item 数（`g1_get_canvas_graph` 的 `data.items`）
2. **数值验证**：抽样看前 2–3 个值是否符合预期公式
3. **视觉验证**：截图，用平行投影正视图看尺寸关系（透视会骗人）

## 5. 本次真机演示的完整复盘（含两个真实坑）

**目标**：用 GH 重做 2026-11-23 手动建的那排「10 个立方体、半径×2」，证明"同样结果、但可编辑"。

**第一次搭（13 对象 / 17 连线 / `solved=true` / 0 报错）→ 读回数据发现两个问题：**

### 坑 1：`Series` 的 `Start` 默认是 0，不是 1

我漏接了 `Start`，序列出来是 `0…9` 而不是 `1…10`。后果：

```
Series 输出 = 0,1,2,…,9
半径 = 0,2,4,…,18      ← 第 1 个半径是 0
边长 = 0,4,8,…,36
Center Box 第 1 项 → "Singular Box"（退化盒，尺寸为 0）
```

**但求解器报 `solved=true`、`reported=0`、没有任何 warning。**
GH 不认为"尺寸为 0 的盒子"是错误——它是合法的退化几何。

> **这是 GH 最重要的认知**：`solved=true` 只表示"没有异常抛出"，**不代表几何有效**。
> 判断对不对必须读数据、看几何。

### 坑 2：`g1_place_slider` 的参数 schema 要求 object 而非 number

单独调用 `place_slider` 时 `min/value/max` 必须是 JSON object 或 null（工具 schema 问题），
而批量接口 `g1_apply_graph` 的 `sliders[]` 里同样的字段传数字却能过。

**处置**：不跟 schema 绕，改用**已验证可用的批量路径** `g1_apply_graph` 重建整图。
代价是重建，好处是路径确定、一次成功、顺便把布局排整齐。

### 修正版（14 对象 / 18 连线 / `solved=true` / 数据全对）

新增一个 `起始序号` 滑块（默认 1）接到 `Series.Start`。读回证据：

| 输出 | 期望 | 实测 |
|---|---|---|
| Series | 1…10 | `1,2` …(10 items) ✓ |
| 半径 | 2,4,…,20 | `2,4` …(10) ✓ |
| 边长 | 4,8,…,40 | `4,8` …(10) ✓ |
| X 位置 | 45,90,…,450 | `45,90` …(10) ✓ |
| 点 | Z = 半径 | `{45,0,2}`, `{90,0,4}` ✓ |
| Center Box | 10 个有效盒 | 10 items，sample 全是 `Box`，无 `Singular Box` ✓ |
| 视口 | 10 个递增、底面齐平 | 平行投影正视图确认 ✓ |
| 文档对象 | 0（GH 不落地） | 0 ✓ |

**这轮的真正收获不是"搭出来了"，而是"读回数据才发现第一个盒子是退化的"**——如果只看 `solved=true` 就交付，就又是一个"技术上成功、结果错了"的案例（参考 `HANDOFF.md` 的方向纠偏复盘）。

## 6. 坑位清单（按症状索引）

| 症状 | 根因 | 处置 |
|---|---|---|
| `solved=true` 但几何不对/退化 | 求解器不校验几何有效性 | 读 `data.items` + 抽样数值 + 截图 |
| 输出数量是 1 不是 N | 输入没接成 list，或上游只出一个值 | 数上游 item 数；必要时 Graft |
| 输出数量是 N 不是 1 | 喂了 list 给只需要单值的输入 | 用 `List Item` 取第 0 项，或 Flatten 前先 `Sort` + `List Item` |
| 数量对但配对错乱 | path 不一致，或 Graft/Flatten 位置错 | 开 `Param Viewer` 看树；挂输出 vs 挂输入要分清 |
| 分支数爆炸（几十个分支） | 对列表 Graft | 先 Flatten 再 Graft，或改用 `Cross Reference` 显式控制 |
| 改一个参数全图卡死 | 分支数随参数指数增长（如双重 Graft） | 用 `参数扫掠` 前先估算数量；必要时拆成两段定义 |
| 视口有、文档没有 | GH 只预览不落地 | 右键组件 → Bake，或用 `Bake` 组件 |
| 组件名搜不到 | obsolete/hidden 被过滤 | `includeDeprecated=true`，或用 Guid |
| GH1 的工具操作 GH2 画布 | 两套 API/两套画布 | 看 `get_context` 的 `version` 字段再选 `g1_*` / `g2_*` |
| 自定义组件"时好时坏" | `SolveInstance` 有副作用 / 读全局状态 | 改成纯函数；数据只从输入来 |

## 7. 什么时候用 GH，什么时候写 C# 插件

这是做插件时最容易判断错的地方（我们已经在 `HANDOFF.md` 犯过一次方向错误）：

| 需求 | 选 GH | 选 C# 插件 |
|---|---|---|
| 探索形态、一次性设计 | ✅ | ❌ 太重 |
| 参数扫掠 / 优化 / Galapagos | ✅ | ❌ 自己实现成本高 |
| 给**会 GH 的人**用 | ✅ | 也可以（打成 cluster） |
| 给**不会 GH 的人**一键完成 | ❌ 要求装 GH + 打开画布 | ✅ 面板 + 命令 |
| 需要精确的 B-rep 手术（Untrim、重缝） | 勉强（`Brep` 组件 + 脚本组件） | ✅ RhinoCommon 直接控制 |
| 需要跨文档、挂文档事件、常驻显示 | ❌ | ✅ DisplayConduit |
| 需要识别"别人做的特征" | ❌ GH 没有逆向识别能力 | ✅ FeatureWorks 那条路 |

**两者的桥梁**：
- GH 定义 → 右键 `Cluster` 打包成一个组件；或存成 user object 给团队复用
- C# 逻辑 → 实现 `GH_Component` 就能变成一个电池（`SolveInstance` 里写几何逻辑）
- 混合：GH 里放 `C# Script` / `Python Script` 组件，既保留数据流又能写循环和条件

**FeatureWorks 为什么不能靠 GH 做**：GH 能"重放"特征，是因为**特征是你用电池建出来的**；
面对导入的哑实体，GH 没有任何"这条边原本是哪次倒角"的信息——那正是 `feature-recognition.md` 第 9 节讲的逆向不适定问题。

## 8. 演示与教学纪律（用户明确要求，长期有效）

用户 2026-11-23 明确：「演示过程可以费一小点 token，教我原理，我们一起改，让它做得更好」。

落地成三条：

1. **先讲这一步在做什么、为什么，再给结果**。不要只丢一个成功截图。
2. **失败也讲清为什么失败**，以及从失败里学到什么（本文件第 5 节就是范例）。
3. **留可变的手柄**：每次交付至少留 3–6 个滑块/参数，让用户能自己拖、自己改；不要交付一个"只能看不能动"的死结果。
4. **一起改**：用户提的想法先落成"构造序列草图"（§4 四步），确认意图后再连电池；不要一上来就搭。
