# 从零到一：基准面四版迭代与渲染场景复盘

> 说明：本文按反馈重新整理，主线聚焦在**基准面（baseline）的从零到一与四个版本的迭代**；**渲染 / IdeaS 场景**部分保留并如实记录了 token 消耗；原稿结尾关于**收益（ROI）**的讨论已按要求删去——那部分偏抽象，放在这里反而冲淡了主题。

## 一、为什么先把基准面立起来

动手做功能之前，我们先把"基准面"定义清楚。基准面不是最终产物，而是一把尺子：它规定输入是什么、输出长什么样、用什么口径判断好坏。

没有基准面，后面每一次改动都说不清是进步还是倒退——尤其是当结果由渲染和模型共同决定、又带着随机性的时候。所以从零到一的第一步，不是堆功能，而是先把这把尺子立住。

## 二、四个版本的迭代

### V1 ｜能跑起来的最小闭环

目标只有一个：**先让它跑通**。

- 确定最小输入契约与输出格式，先把链路从"想法"到"渲染结果"打通。
- 建立最原始的基准面：一组固定的输入样例 + 一套能自动跑出结果的脚本。
- 此时的产出很粗糙，但它回答了最关键的问题——**这条路能不能走通**。

V1 的价值不在效果，而在于把不确定的事情变成了可观察的事情。

### V2 ｜把基准变成一把可复现的尺子

能跑通之后，问题变成："同样的输入，两次结果一样吗？"

- 固定随机种子、固化提示词与参数，让结果尽量可复现。
- 给基准面加上回归对比能力：每次改动都能和上一版直接比。
- 把散落的判断标准收敛成明确的指标，减少"凭感觉说变好了"。

这一版之后，基准面才真正从"能看"升级为"能量"。迭代开始有据可依，而不是拍脑袋。

### V3 ｜场景化：接入 IdeaS 渲染链路

基准面稳了，开始往真实场景走——也就是 **IdeaS 场景**。

- 把 IdeaS 场景接进来，打通从输入到渲染的完整链路。
- 渲染这一层在本版正式成为主角：结果的可读性、一致性、细节都靠它呈现。
- 也正是在这一版，**token 消耗的问题开始暴露**（详见下一节）。

V3 是从"实验室基准"走向"真实场景"的关键一跃，同时也把成本和效果的矛盾摆上了台面。

### V4 ｜收敛：从能用到好用

最后一版不再追求加东西，而是收口。

- 针对 V3 暴露的 token 问题做优化：减少无效往返、复用中间结果、控制上下文膨胀。
- 把前几版验证有效的做法固化下来，去掉临时性的补丁。
- 让整条链路在效果、稳定性与成本之间达到一个可接受的平衡。

四个版本走完，基准面也完成了它的使命：从"能不能做"到"做得稳不稳"，再到"场景里跑不跑得动"。

## 三、渲染：IdeaS 场景的 token 账

渲染这部分不用多解释——它的作用就是把基准面的结果真正呈现出来，让好坏一眼可见。

真正值得记的是 **IdeaS 场景里的 token 消耗**。它高，主要有几个原因：

- **多轮迭代**：一个场景往往要反复渲染、反复调整，每一轮都带着完整上下文。
- **上下文累积**：历史对话、中间结果、渲染反馈不断堆叠，越往后单次调用越重。
- **渲染链路本身**：结果需要被再次描述、解析、回喂，额外增加了往返次数。

这直接影响了 V4 的优化方向——不是去砍效果，而是**把无效的 token 花销挤掉**：该缓存的缓存、该复用的复用、该截断的截断。渲染质量要保，但成本不能失控。

## 四、小结

从零到一这条路，真正的主线其实只有一条：**先把基准面立住，再让每一次迭代都踩在它上面**。

- V1 解决"能不能跑"；
- V2 解决"可不可复现"；
- V3 走向真实场景，也暴露了渲染的 token 成本；
- V4 收口，把效果和成本拉回平衡。

关于收益的部分这次没有放进来——它需要更扎实的数据支撑，等有了真实场景的量化结果，再单独成篇更合适。
